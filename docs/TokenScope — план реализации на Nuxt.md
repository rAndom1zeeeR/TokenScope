# TokenScope — план реализации на Nuxt

## Как работать по плану

Проект делится на 13 этапов, и каждый заканчивается чем-то, что можно запустить и показать. До этапа 6 данные моковые, с этапа 7 появляется настоящая база, с этапа 8 — настоящая сеть Solana.

Правила, которые превращают проект в обучение, а не в копирование:

1. **Пишете сами.** Я объясняю, показываю форму решения и ревьюю ваш код, но руки на клавиатуре ваши. Если скопировали фрагмент, закройте его и перепишите по памяти.
2. **Один этап — одна ветка.** Ветка `stage-3-token-page`, коммиты по Conventional Commits, в конце merge в `main` с описанием, что вы поняли. Это же потом показывает работодателю историю роста.
3. **Не идёте дальше, пока не выполнен критерий готовности.** Он в конце каждого этапа и проверяется руками: «открываю страницу, вижу вот это».
4. **Сначала документация, потом код.** В каждом этапе есть блок «Что изучить»: 20–40 минут чтения на nuxt.com или vuejs.org экономят часы отладки.
5. **Один намеренный эксперимент на этап.** Сломайте что-нибудь (уберите `key`, верните не тот тип, выключите SSR на странице) и посмотрите, что произошло. Так запоминаются границы возможностей.

Каждый этап описан одинаково: цель, что изучить, шаги, критерий готовности, типичные ошибки и вопросы самопроверки. Если на вопрос самопроверки не можете ответить своими словами, вернитесь к документации, а не двигайтесь дальше.

## Архитектура и структура репозитория

Один Nuxt-проект отдаёт и сайт, и API, и фоновые задачи. Один и тот же Docker-образ запускается в двух ролях: `web` отвечает на запросы, `worker` только индексирует данные. Между ними общение идёт через Postgres: ни Redis, ни отдельных очередей нет.

В Nuxt 4 код интерфейса живёт в `app/`, серверный код в `server/`, а код, общий для обоих, в `shared/`. Для каждой из этих частей создаётся свой TypeScript-проект, поэтому типы с сервера попадают в компоненты через `shared/types`, без кодогенерации.

```
tokenscope/
├─ app/
│  ├─ assets/css/tokens.css      # токены дизайна (цвета, отступы, шрифты)
│  ├─ components/                # UI-кирпичики и блоки страниц
│  ├─ composables/               # useTokenTraders, useWallet, useLiveSwaps
│  ├─ layouts/default.vue        # шапка, поиск, контейнер
│  ├─ pages/
│  │  ├─ index.vue               # Главная
│  │  ├─ token/[address]/
│  │  │  ├─ index.vue            # Traders
│  │  │  ├─ holders.vue
│  │  │  ├─ transfers.vue
│  │  │  └─ links.vue
│  │  └─ wallet/[address]/
│  │     ├─ index.vue            # Overview
│  │     ├─ trades.vue
│  │     └─ transfers.vue
│  ├─ app.vue
│  └─ error.vue
├─ server/
│  ├─ api/                       # эндпоинты: tokens/, wallets/
│  ├─ db/                        # схема Drizzle, миграции, клиент
│  ├─ mock/                      # генератор моков (этапы 2–6)
│  ├─ services/                  # PnL, кластеры, Helius-клиент
│  ├─ tasks/                     # Nitro tasks для индексатора
│  └─ plugins/                   # запуск роли worker
├─ shared/
│  ├─ types/                     # Swap, Transfer, TraderPosition, WalletGraph…
│  └─ utils/                     # форматирование чисел и адресов
├─ nuxt.config.ts
└─ docker-compose.yml            # web, worker, postgres
```

Соответствие макетов страницам: Main → `pages/index.vue`; четыре вкладки токена (Traders, Holders, Transfers, Links) → вложенные страницы в `pages/token/[address]/`; три вкладки кошелька (Overview, Trades, Transfers) → `pages/wallet/[address]/`. Общая шапка вкладок и заголовок токена или кошелька выносятся в родительский компонент с `<NuxtPage />`. Мобильные макеты не отдельные страницы: это те же компоненты с адаптивной вёрсткой (этап 5).

Роль процесса задаётся переменной `NUXT_ROLE`. При значении `worker` серверный плагин запускает индексатор и расписание Nitro tasks, а при `web` только отдаёт API и страницы. Новые свопы worker пишет в Postgres и сообщает вебу через `LISTEN/NOTIFY`, а веб транслирует их браузеру по SSE (этап 11).

Два принципа, которые стоит держать с первого дня: страницы не ходят за данными напрямую, а только через composables, которые вызывают `/api/*`; и API возвращает ровно те типы из `shared/types`, что приходят в компоненты. Тогда замена моков на реальные данные в этапе 7 затрагивает только `server/`, а фронт не меняется.

## Этап 0. Окружение и скелет проекта

**Цель.** Пустой Nuxt 4 проект с линтером, типами и первым коммитом, который запускается одной командой.

**Что изучить.** Что такое Nuxt и чем он отличается от голого Vue + Vite (файловый роутинг, автоимпорты, SSR); структуру каталогов Nuxt 4; `<script setup lang="ts">` и Composition API. Начните с официального туториала Vue и раздела Getting Started в документации Nuxt.

**Шаги.**

1. Поставьте Node 22 LTS и pnpm (`corepack enable`). Проверьте: `node -v`, `pnpm -v`.
2. Создайте проект: `pnpm dlx nuxi@latest init tokenscope`, выберите pnpm и инициализацию git. Запустите `pnpm dev` и откройте `localhost:3000`.
3. Включите строгий TypeScript и проверку типов в `nuxt.config.ts`: `typescript: { strict: true }`. Добавьте скрипт `"typecheck": "nuxi typecheck"`.
4. Подключите линтер: `pnpm dlx nuxi module add eslint`, затем Prettier. Настройте `lint` и `format` в `package.json`.
5. Добавьте модули, которые понадобятся сразу: Tailwind CSS, `@vueuse/nuxt`, `@pinia/nuxt`, `@nuxt/fonts`. Остальное подключайте по мере надобности, а не заранее.
6. Создайте структуру из раздела про архитектуру: пустые папки `app/components`, `app/composables`, `shared/types`, `server/api`. В Git пустые папки не хранятся, поэтому кладите в них `.gitkeep`.
7. Настройте git-хуки (husky + lint-staged) и Conventional Commits. Сделайте первый коммит: `chore: init nuxt 4 project`.
8. Заведите `README.md` с одной строкой запуска и описанием проекта. Это заготовка для финального README.

**Критерий готовности.** `pnpm dev`, `pnpm lint` и `pnpm typecheck` проходят без ошибок на чистом клонировании репозитория. Репозиторий опубликован на GitHub.

**Типичные ошибки.**

- Ставить десяток модулей «на вырост». Каждый лишний модуль потом придётся объяснять на собеседовании.
- Класть код в корневые `components/` и `pages/` вместо `app/`. В Nuxt 4 они не подхватятся.
- Отключить строгие типы, чтобы «не мешали». Потом ошибки всплывут все сразу.

**Вопросы самопроверки.** Что произойдёт, если создать файл `app/pages/about.vue`? Откуда в компоненте берётся `ref` без импорта? Чем `app/` отличается от `server/` с точки зрения TypeScript-проектов?

## Этап 1. Фундамент UI: токены, layout, роутинг

**Цель.** Каркас сайта: тёмная тема по макету, общий layout с шапкой и поиском, все 11 маршрутов открываются и показывают заглушки. Данных пока нет.

**Что изучить.** Файловый роутинг Nuxt (динамические сегменты `[address]`, вложенные маршруты и `<NuxtPage />`); layouts и `<NuxtLayout>`; `<NuxtLink>`; CSS-переменные и Tailwind; props, emits и slots в компонентах Vue; `defineModel`.

**Шаги.**

1. Перенесите цвета, радиусы, отступы и шрифты из макета в `app/assets/css/tokens.css` как CSS-переменные (`--bg`, `--surface`, `--text`, `--muted`, `--profit`, `--loss`, `--accent`). Подключите файл в `nuxt.config.ts` через `css: [...]` и свяжите переменные с темой Tailwind.
2. Создайте `app/layouts/default.vue`: шапка с логотипом, полем поиска по адресу и контейнером ограниченной ширины, внутри `<slot />`.
3. Создайте страницы-заглушки по структуре из раздела про архитектуру. Во вложенных маршрутах токена и кошелька родительский файл (`token/[address].vue`) держит заголовок и вкладки, а дочерние рисуются через `<NuxtPage />`.
4. Сделайте компонент `TabsNav.vue`: получает список вкладок, подсвечивает активную по `useRoute()`. Не передавайте активную вкладку пропсом, активный маршрут и есть её состояние.
5. Соберите базовые компоненты по макетам: `UiButton`, `UiBadge` (теги кошельков), `UiCard`, `UiStat` (число с подписью и дельтой), `UiTable` (пока только оболочка), `UiSkeleton`. Каждый с типизированными props через `defineProps<{...}>()`.
6. Поиск в шапке: при вводе адреса и Enter вызывайте `navigateTo('/token/' + address)`. Валидацию адреса Solana добавите позже (этап 2).
7. Подключите страницу `error.vue` для 404 и ошибок.
8. Для каждого базового компонента сделайте страницу `/dev/ui` (только в dev) со всеми состояниями. Позже её заменит Storybook или Histoire.

**Критерий готовности.** Все маршруты открываются по прямой ссылке и по клику во вкладках. Обновление страницы на `/token/abc/links` не даёт 404. Цвета нигде не прописаны литералами, только через переменные. Layout визуально совпадает с шапкой макета.

**Типичные ошибки.**

- Копировать вёрстку макета целиком в одну страницу. Дробите на компоненты сразу, пока их три, а не тридцать.
- Хранить активную вкладку в `ref`. Она рассинхронизируется с URL при перезагрузке.
- Мешать стили токенов и компонентов. Токены только переменные, всё остальное в компонентах.

**Вопросы самопроверки.** Чем layout отличается от обычного родительского компонента? Почему у вложенного маршрута родитель должен содержать `<NuxtPage />`? Что даст `defineProps` с типом по сравнению с массивом строк?

## Этап 2. Типы, zod, генератор моков и мок-API на Nitro

**Цель.** Контракт данных между фронтом и бэком зафиксирован типами. Nitro отдаёт правдоподобные моковые данные по тем же URL, по которым позже будут отдаваться реальные.

**Что изучить.** Server routes в Nitro (`defineEventHandler`, `getRouterParam`, `getQuery`); `$fetch` и `useFetch` / `useAsyncData`; TypeScript: `type` против `interface`, дискриминированные объединения, `satisfies`; zod для валидации входа; детерминированная генерация данных (faker с фиксированным seed).

**Шаги.**

1. Опишите сущности в `shared/types/` по одному файлу: `swap.ts`, `transfer.ts`, `trader.ts`, `wallet.ts`, `token.ts`, `graph.ts`, `common.ts` (`Page<T>`). Суммы храните как `string` или `bigint` в минимальных единицах, а в числа переводите только на границе отображения: так вы не потеряете точность.
2. Опишите теги кошельков как объединение строк: `type WalletTag = 'sniper' | 'deployer' | 'whale' | 'smart' | 'bundled' | 'lp' | 'cex' | 'bot'`.
3. Сделайте zod-схемы для параметров запросов в `shared/schemas/`: адрес Solana (base58, длина 32–44), `page`, `limit`, `sort`, `order`, `range`. Типы входа выводите из схем через `z.infer`.
4. Установите `@faker-js/faker`. В `server/mock/` напишите генератор с seed, который зависит от адреса токена. Тогда один и тот же адрес всегда даёт одни и те же данные:

```ts
// server/mock/seed.ts
import { faker } from '@faker-js/faker'

export function seededFaker(key: string) {
	let h = 0
	for (const ch of key) h = (h * 31 + ch.charCodeAt(0)) >>> 0
	faker.seed(h)
	return faker
}
```

5. Согласуйте данные между собой. Сумма балансов холдеров не должна превышать supply, адрес токена не должен совпадать с адресом кошелька, цена в переводах должна соответствовать цене в свопах. Эти ошибки первыми бросаются в глаза на демо.
6. Создайте эндпоинты, по одному на запрос страницы: `GET /api/tokens/[address]`, `/traders`, `/holders`, `/transfers`, `/graph`, `/candles`; `GET /api/wallets/[address]`, `/trades`, `/transfers`; `GET /api/home` для главной. Входные параметры прогоняйте через `schema.parse` в начале обработчика.
7. Добавьте искусственную задержку 200–600 мс в мок-API, чтобы увидеть состояния загрузки, и параметр `?fail=1` для проверки ошибок.
8. Напишите composables в `app/composables/`, по одному на группу данных: `useTokenTraders(address, query)` и так далее. Внутри `useFetch` с типом ответа из `shared/types`. Страницы будут знать только про composables.

**Критерий готовности.** Каждый эндпоинт отвечает корректным JSON за разумное время. Типы ответа видны в редакторе по наведению на `data.value`. Невалидный адрес даёт 400 с понятным сообщением. Два запроса с одним адресом возвращают одинаковые данные.

**Типичные ошибки.**

- Описывать типы дважды: на сервере и на клиенте. Источник один, `shared/types`.
- Использовать `Math.random()` для моков. Данные скачут между перезагрузками, и баги не воспроизводятся.
- Класть `useFetch` в обработчики событий. Он рассчитан на `setup`, для запросов по клику используйте `$fetch`.
- Ключ `useFetch` не зависит от параметров. Передавайте реактивные `query`, и запрос перезапустится сам.

**Вопросы самопроверки.** Чем `useFetch` отличается от `$fetch`? Зачем нужен ключ в `useAsyncData`? Почему суммы в токенах не стоит хранить в `number`?

## Этап 3. Страницы на моках: Главная, Токен, Кошелёк

**Цель.** Все 11 экранов собраны по макетам и работают на мок-API: таблицы, фильтры, сортировка, пагинация, состояния загрузки и ошибок. Графики пока заглушки.

**Что изучить.** Реактивность (`ref`, `computed`, `watch`, `toRef`); `useFetch` с реактивными параметрами; синхронизация фильтров с URL через `useRoute().query` и `navigateTo`; `<Suspense>` и `status` у `useFetch`; TanStack Table для таблиц, TanStack Virtual для длинных списков; `v-model` на собственных компонентах.

**Шаги.**

1. Начните с Главной: блок со сводкой, список трендовых токенов, поиск. Данные из `useHome()`. Соберите страницу из готовых `UiCard` и `UiStat`, а не из сырой вёрстки.
2. Сделайте шапку токена (`TokenHeader.vue`) в родительском маршруте `token/[address].vue`: имя, цена, объём, ликвидность, число трейдеров. Данные грузятся один раз, вкладки их не перезапрашивают.
3. Вкладка Traders: таблица на TanStack Table с колонками кошелька, объёма, PnL, баланса и тегов. Сортировка и страница хранятся в query-параметрах URL, поэтому ссылку можно отправить другу.
4. Фильтры (по тегу, по профитным и убыточным, по диапазону объёма) вынесите в `TraderFilters.vue` с `v-model`. Любое изменение фильтра сбрасывает страницу на первую.
5. Вкладки Holders и Transfers повторяют тот же паттерн. Выделите общий `DataTable.vue`, когда увидите второе повторение, а не раньше.
6. Вкладку Links пока оставьте с заглушкой под граф (этап 4).
7. Страница кошелька: шапка с PnL и тегами, вкладки Overview, Trades, Transfers. Для длинной ленты сделок подключите виртуализацию.
8. На каждой странице реализуйте три состояния: загрузка (скелетон по форме таблицы), ошибка (кнопка «повторить») и пустой результат. Это то, что в портфолио смотрят в первую очередь.
9. Форматирование вынесите в `shared/utils/format.ts`: `formatUsd`, `formatPct`, `shortAddress`, `formatAge`. Тестировать их проще всего, они чистые функции.

**Критерий готовности.** Каждый экран похож на макет при ширине 1440. Фильтры и сортировка переживают перезагрузку страницы. Любой запрос можно «сломать» через `?fail=1`, и интерфейс красиво покажет ошибку. Нигде нет `any`.

**Типичные ошибки.**

- Дублировать запрос в шапке и вкладке. Данные шапки берите из одного места.
- Мутировать props. Для изменения используйте `emit` или `defineModel`.
- Фильтровать и сортировать на клиенте массив из 10 000 строк. Это работа сервера, клиент получает уже готовую страницу.
- Вшить в таблицу бизнес-логику. Таблица только показывает то, что ей дали.

**Вопросы самопроверки.** Что произойдёт при смене `address` в маршруте, если страница использует `useFetch`? Зачем хранить фильтры в URL, а не в `ref`? Чем `computed` отличается от `watch` и когда нужен каждый?

## Этап 4. Графики и граф связей

**Цель.** Свечной график с маркерами сделок, кривая PnL кошелька и интерактивный граф связей между кошельками.

**Что изучить.** Жизненный цикл компонента (`onMounted`, `onBeforeUnmount`) и `template ref`; как обёрнуть императивную библиотеку в компонент Vue; `<ClientOnly>` и почему canvas не работает на сервере; `shallowRef` для тяжёлых объектов; lightweight-charts, Sigma.js и graphology.

**Шаги.**

1. Установите `lightweight-charts`. Сделайте `PriceChart.vue`: создаёт график в `onMounted`, реагирует на изменение props через `watch`, удаляет его в `onBeforeUnmount` и подстраивается под размер контейнера (`useResizeObserver` из VueUse).
2. Нанесите маркеры покупок и продаж кошелька на график токена. Данные маркеров приходят с сервера как `TradeMarker[]`.
3. `PnlChart.vue` для страницы кошелька: линия или область с цветом `--profit` выше нуля и `--loss` ниже. Покажите именно то, что в продукте главное: в какой момент кошелёк был в плюсе.
4. Обёрните оба графика в `<ClientOnly>` с заглушкой-скелетоном той же высоты, чтобы страница не прыгала.
5. Установите `sigma` и `graphology`. Сделайте `WalletGraph.vue`: узлы — кошельки (размер по объёму, цвет по кластеру), рёбра — переводы токена. Раскладку считайте через ForceAtlas2 на клиенте.
6. Добавьте взаимодействие: наведение подсвечивает соседей, клик открывает боковую панель кошелька, двойной клик переходит на его страницу.
7. На большом графе (от 500 узлов) проверьте производительность. При необходимости ограничьте выборку на сервере (топ-N по объёму).

**Критерий готовности.** Переход между страницами не оставляет в памяти старых графиков (проверьте вкладкой Memory в DevTools). Ресайз окна меняет размер графика. Граф связей плавно работает на сотнях узлов.

**Типичные ошибки.**

- Создавать график на сервере. Библиотеке нужен `window`, создавайте его только в `onMounted`.
- Хранить экземпляр графика в `ref`. Vue проксирует его глубоко, для таких объектов нужен `shallowRef`.
- Забыть очистку в `onBeforeUnmount`. Если её нет, утечки памяти накапливаются при каждом переходе.

**Вопросы самопроверки.** Для чего нужен `<ClientOnly>` и что такое гидратация? В чём разница `ref` и `shallowRef`? В каком хуке должна жить очистка подписки на ресайз?

## Этап 7. Postgres и Drizzle: схема данных

**Цель.** Моки заменены чтением из базы. Данные в базе пока залиты сидером, фронт не изменился.

**Что изучить.** Основы SQL: индексы, агрегаты, `GROUP BY`, оконные функции; Drizzle ORM (схема как TypeScript, `drizzle-kit`, миграции); пул соединений; почему время в `timestamptz`, а деньги в `numeric`.

**Шаги.**

1. Поднимите Postgres в `docker-compose.yml` и добавьте `DATABASE_URL` в `.env` и `runtimeConfig`.
2. Установите `drizzle-orm`, `postgres` и `drizzle-kit`. В `server/db/schema.ts` опишите таблицы:

```ts
export const swaps = pgTable(
	'swaps',
	{
		signature: text('signature').primaryKey(),
		token: text('token').notNull(),
		wallet: text('wallet').notNull(),
		side: text('side', { enum: ['buy', 'sell'] }).notNull(),
		amountToken: numeric('amount_token').notNull(),
		amountUsd: numeric('amount_usd').notNull(),
		ts: timestamp('ts', { withTimezone: true }).notNull(),
	},
	(t) => [index('swaps_token_ts').on(t.token, t.ts), index('swaps_wallet_ts').on(t.wallet, t.ts)],
)
```

3. Остальные таблицы: `transfers`, `tokens`, `wallets`, `trader_positions` (материализованные итоги по кошельку и токену), `pnl_points`, `indexer_cursor` (на какой подписи остановился индексатор).
4. Сгенерируйте и примените миграцию: `drizzle-kit generate`, затем `drizzle-kit migrate`. Храните миграции в git.
5. Напишите `scripts/seed.ts`, который переносит вывод мок-генератора в базу.
6. Смените реализацию обработчиков в `server/api` на запросы к базе через слой `server/services/*`. Контракт ответов не меняется.
7. Пагинацию и сортировку делайте в SQL (`ORDER BY`, `LIMIT`, `OFFSET`; позже keyset). Проверьте `EXPLAIN` на самом тяжёлом запросе.

**Критерий готовности.** Страницы выглядят так же, как на моках, но данные приходят из Postgres. Сброс базы и повторный seed восстанавливают проект за минуту. Тяжёлые запросы идут по индексу, а не по полному скану.

**Типичные ошибки.**

- Хранить деньги в `float`. Используйте `numeric`.
- Делать индексы «на всякий случай». Индексы замедляют запись, выбирайте их по реальным запросам.
- Ручные правки базы без миграций. Тогда команда и деплой разойдутся с локальной базой.

**Вопросы самопроверки.** Почему `numeric`, а не `float`? Какой индекс ускорит список сделок кошелька? Чем `OFFSET` плох на больших таблицах?

## Этап 8. Индексатор: Helius и Nitro tasks

**Цель.** Реальные свопы и переводы токена Solana попадают в ту же базу, куда раньше лились моки. Индексатор работает в роли `worker`.

**Что изучить.** Как устроены транзакции Solana (подпись, инструкции, token balances до и после); `@solana/kit` и RPC; парсинг DEX-свопов (Jupiter, Raydium, Pump); Helius (Enhanced Transactions / webhooks); Nitro tasks и `scheduledTasks`; идемпотентность и курсоры.

**Шаги.**

1. Заведите бесплатный ключ Helius. Храните его только в `.env` и `runtimeConfig` (не в `public`), в репозиторий попадает только `.env.example`.
2. Руками разберите одну транзакцию свопа в обозревателе (Solscan), а потом ту же в ответе вашего клиента. Понять, откуда берётся направление и сумма, важнее любой библиотеки.
3. Напишите клиент в `server/services/helius.ts`: выборка транзакций токена постранично с курсором, повторы с ожиданием при 429, ограничение параллельных запросов.
4. Сделайте парсер `parseSwap(tx): Swap | null` как чистую функцию без сети и покройте её тестами на реальных транзакциях из фикстур. Непонятные транзакции пропускайте с логом, не падайте.
5. Включите задачи Nitro и расписание:

```ts
// nuxt.config.ts
nitro: {
  experimental: { tasks: true },
  scheduledTasks: { '*/1 * * * *': ['indexer:sync'] },
}
```

```ts
// server/tasks/indexer/sync.ts
export default defineTask({
	meta: { name: 'indexer:sync', description: 'Подтянуть новые свопы по курсору' },
	async run() {
		// читаем курсор → тянем страницу → parseSwap → upsert → двигаем курсор
		return { result: 'ok' }
	},
})
```

6. Выполняйте задачу только в роли `worker`: в `web` расписание не должно запускаться. Ручной запуск удобен для отладки: `runTask('indexer:sync')`.
7. Запись делайте идемпотентно: `INSERT ... ON CONFLICT (signature) DO NOTHING`. Повторный прогон не должен дублировать строки.
8. Сначала проиндексируйте один небольшой токен за несколько дней. Его можно сверить с внешними сервисами (выберите 2–3 демо-токена).

**Критерий готовности.** Демо-токен индексируется до конца и повторный запуск не меняет число строк. Процесс переживает перезапуск и продолжает с курсора. Число свопов совпадает с обозревателем в пределах разумной погрешности.

**Типичные ошибки.**

- Публиковать API-ключ. Если ключ утёк, перевыпустите его, а историю git очистите.
- Парсить всё подряд. Начните с одного DEX, остальные добавляйте по одному.
- Расчёт цены без учёта децималов токена. Суммы в минимальных единицах нужно делить на `10^decimals`.

**Вопросы самопроверки.** Как понять, кто купил, а кто продал, по изменению балансов? Для чего нужен курсор и что будет без идемпотентности?

## Этап 9. Расчёт PnL

**Цель.** Для каждого трейдера: реализованный и нереализованный PnL, объём, баланс и кривая «когда был в плюсе».

**Что изучить.** Метод средней стоимости (average cost) и его отличие от FIFO; что такое реализованный и нереализованный результат; точная арифметика в JS (`bigint` или `decimal.js`); оконные функции SQL.

**Шаги.**

1. Опишите формулы на бумаге с несколькими покупками и продажами. При покупке пересчитайте среднюю цену входа, при продаже фиксируйте реализованный результат от разницы цены и проданного объёма.
2. Напишите чистую функцию `computePositions(swaps: Swap[]): TraderPosition[]`. Она не знает ни про базу, ни про Nuxt.
3. Покройте её тестами с ручными примерами: покупка → продажа в плюс, в минус, частичная продажа, продажа без покупки (токены пришли переводом).
4. Стройте точки `pnl_points` по времени: каждая точка — PnL кошелька по токену на момент сделки (нереализованный считайте по цене такого же момента).
5. Запускайте пересчёт как другую задачу Nitro (`pnl:recompute`) после индексатора, инкрементально только для затронутых кошельков.
6. Сверьте топ-10 кошельков с Birdeye или Moralis на демо-токене. Расхождения нормальны (у всех разные методы), но их нужно объяснить в README.

**Критерий готовности.** Юнит-тесты на ручных примерах зелёные. Для демо-токена топ-кошельки совпадают с внешними сервисами по знаку и по порядку величины. Расчёт не зависит от порядка записей в базе.

**Типичные ошибки.**

- Считать деньги в `number`. На больших суммах появляются погрешности.
- Считать сделки без сортировки по времени и слоту. Порядок операций меняет результат.
- Игнорировать токены, пришедшие переводом. Без них баланс и PnL не сойдутся.

**Вопросы самопроверки.** Чем average cost отличается от FIFO на примере трёх сделок? Как считать PnL, если кошелёк получил токены без покупки?

## Этап 10. Связи и кластеры кошельков

**Цель.** Граф переводов токена между кошельками строится из реальных данных, а связанные кошельки объединяются в кластеры с понятными признаками.

**Что изучить.** Теория графов: компоненты связности, union-find; рекурсивные запросы SQL (`WITH RECURSIVE`); эвристики кластеризации кошельков.

**Шаги.**

1. Определите рёбра: прямой перевод токена между двумя кошельками; вес ребра — сумма и число переводов. Исключите адреса бирж и пулов ликвидности, иначе граф слипнется в один ком.
2. Напишите сервис `buildWalletGraph(token, options)`, который возвращает тот же `WalletGraph`, что и мок. Фронт не правится.
3. Кластеры: однотипные переводы от одного источника, покупки в один слот (bundled), общий финансирующий кошелёк. Каждый признак — отдельная функция, не группируйте всё в одну проверку.
4. Присвойте теги (`sniper`, `deployer`, `whale`, `smart`, `bundled`, `lp`, `cex`, `bot`) по прозрачным правилам и вынесите правила в конфиг, чтобы их можно было обсудить и поменять.
5. Ограничьте размер графа (глубина, топ-N по объёму) и кэшируйте результат в базе: граф пересчитывается в задаче, не на каждый запрос.

**Критерий готовности.** Вкладка Links показывает реальный граф демо-токена без единого изменения во фронте. Каждый тег и каждую связь можно объяснить: по какому правилу он появился. Граф строится за адекватное время.

**Типичные ошибки.**

- Включать в граф биржи и пулы. Они соединяют тысячи несвязанных кошельков.
- Подавать эвристику как доказанный факт. В интерфейсе скажите «возможно связаны», а не «один владелец».

**Вопросы самопроверки.** В чём смысл union-find и где он применим? Какие ложные срабатывания даёт такая эвристика?

## Этап 11. Реалтайм

**Цель.** Новые сделки появляются в таблице без перезагрузки страницы.

**Что изучить.** Server-Sent Events и их отличие от WebSocket; `EventSource` в браузере; `LISTEN/NOTIFY` в Postgres; очистка подписок в `onScopeDispose`.

**Шаги.**

1. После записи партии свопов worker вызывает `NOTIFY new_swaps, '<token>'`.
2. В `web` одно соединение слушает канал через `LISTEN`. Обработчик `GET /api/tokens/[address]/stream` отдаёт поток SSE (`createEventStream`), фильтруя по токену.
3. На клиенте сделайте composable `useLiveSwaps(address)` на `useEventSource` из VueUse. Он не должен писать в таблицу напрямую, а отдаёт список новых свопов.
4. Ограничьте ленту (например, последние 200 строк) и добавьте кнопку паузы, чтобы таблица не прыгала под курсором.
5. Обработайте обрыв соединения: автопереподключение и индикатор «связь потеряна».

**Критерий готовности.** Вы открываете две вкладки браузера, в одной worker вставляет своп, в другой он появляется за секунду–две. При закрытии вкладки соединение закрывается.

**Типичные ошибки.**

- Держать незакрытые соединения к БД на каждого клиента. Слушатель `LISTEN` один, клиентам он раздаёт данные в памяти.
- Не чистить подписку при размонтировании компонента.

**Вопросы самопроверки.** Почему для одностороннего потока хватает SSE? Какие ограничения у `NOTIFY` по размеру сообщения и как их обойти?
